Executive Summary
Sovereign Agentic AI (SIH26117) calls for a self‑contained AI workbench that uses open‑weight multimodal
LLMs entirely within an organization’s perimeter for confidential industrial tasks. In practice, we will
deliver a working prototype (code, UI, docs and demo) of an on‑premise AI agent platform, including
front‑end, backend, local model inference, retrieval (vector DB), agent orchestration and security controls.
The system will never call external LLM APIs or cloud services, thereby preserving data sovereignty
【13†L318-L322】【31†L51-L59】. 
The minimum hackathon MVP will allow a judge to upload or query a confidential document (e.g. an
industrial report or diagram), and see our system (a) retrieve relevant data, (b) run agentic LLM workflows
(question answering, summarization, report generation, etc.), and (c) output results – all with demonstrable
audit trails. We use open‑source LLMs (e.g. Meta Llama 3, Mistral, Qwen) so no proprietary weights leave
the site【13†L318-L322】【35†L220-L226】. The solution includes logging, RBAC and (optionally) a Trusted
Execution Environment (TEE) to prove code/data are shielded【33†L46-L49】. 
Below is a complete breakdown:
1. Problem Statement & Deliverables
Problem (official phrasing): Build a “Sovereign On-Premise Agentic AI Workbench using Open-Weight
Multimodal LLMs for Confidential Industrial Work”【3†L831-L834】. In plain terms: the team must
design and implement an AI system that runs entirely on-site (on-premise or air-gapped), using open-
source (“open-weight”) large language models (LLMs) and vision-language models. It should orchestrate
multiple AI “agents” to perform industrial workflows (e.g. analyzing equipment manuals, generating
reports, answering queries) on sensitive data. All computation – LLM inference, data retrieval, agent
orchestration – must happen within the organization’s infrastructure under its control【31†L51-L59】
【13†L318-L322】. There must be no external calls to third-party AI services, ensuring data privacy and
regulatory compliance【13†L318-L322】【31†L51-L59】. 
Key deliverables (official/expected): A complete software prototype including: 
User Interface & API: A simple UI (e.g. web app or CLI) for inputting documents or queries, and
viewing AI outputs. 
Core Engine: Local LLM(s) and retrieval system (vector DB) with RAG capabilities; agent workflow
engine (e.g. using LangChain) that can call tools and LLMs. 
Multimodal Support: Capability to process both text and images (diagrams, schematics). 
Security & Deployment: On-premise deployment (e.g. Docker containers or local servers), with
audit logging, role-based access control, and evidence of no egress. Optionally integrate TEE (Intel
SGX/AMD SEV) for extra trust.

2. MVP Features & 36h Demo Script
MVP Feature List
Secure Upload/Input: Judge can upload a PDF or image (e.g. machine manual, process flowchart) or
enter a text query, via a web UI. Input is tagged as “confidential – internal use only.” 
Document Ingestion & Indexing: The system ingests the input document(s), runs OCR if needed,
and stores vector embeddings in a local database. (Offline step or on-the-fly for demo.) 
Agent Workflow Engine: A multi-step pipeline (or “agent”) that processes the query:
Retrieval: Use vector search over the ingested docs to fetch relevant passages/images. 
Multimodal LLM Inference: Feed text and image context into an open LLM or vision-language model.
(For example, use BLIP-2 or LLaVA model, or text + alt text from images.) 
Task-specific Agents: Specialized sub-agents can handle tasks like summarization, Q&A, or report
writing. For instance, a “Query Answering Agent” uses LLM to answer the judge’s question; a “Report
Generation Agent” composes a PDF report. 
Tool Use: Agents may call local tools (e.g. a calculator, internal API) as needed. 
Explainability & Trace: For each step, the system logs which documents and LLM outputs were
used, providing transparency (e.g. “Citing pages 12-14 of manual” or “using tool X to compute Y”). 
Output & Feedback: The final answer/summary is displayed in the UI. Judges can see confidence
scores or reasons (optional “why this answer” to show auditability). 
Security Controls: Demonstrate that no external network requests leave the system (e.g. show
disabled internet). Role-login screen (admin vs user) ensures only authenticated person can query. 
Optional TEE Demo: If time allows, show a pop-up or diagram of “Intel SGX enclave” running LLM
inference – proving hardware-based isolation【33†L46-L49】.

Web UI / API Server: A simple front-end (could be React or Flask) where users submit queries/
documents. It calls the backend APIs. 
Backend / Agent Engine: Hosts orchestration logic (e.g. using a Python microservice). It manages
agent workflows and calls other components. 
Local LLM Server: Runs one or more open LLMs (e.g. Meta Llama 3, Mistral, Qwen) for inference.
This may be a separate service (using vLLM or llama.cpp) that the backend queries【35†L220-L226】.
Vector Database (RAG layer): Stores embeddings of confidential documents. On query, it retrieves
top-k relevant passages to feed into the LLM. We choose an on-prem DB like Weaviate or Milvus
(open-source, with GPU acceleration). 
Agent Orchestration: Implements multi-step workflows. For example, using LangChain or a custom
engine, each “agent” can call the LLM, the DB, or local tools (e.g. formula calculators). We enforce
policies here (which agents can run which tools). 
Local Tools/APIs: Intranet services or computation modules (e.g. an offline image OCR, a local
knowledge API, or even system commands), callable by agents. E.g. Tesseract OCR or a rules engine. 
Audit & Logging: Every query, prompt, retrieval result and tool action is logged in a secure log store
(e.g. Elasticsearch with Kibana or just files) for compliance and debugging. 
Security Layer / TEE (Optional): Ideally, the LLM server or critical agents run inside a trusted
enclave (Intel SGX or AMD SEV) to cryptographically attest that data and model never leave protected
memory【33†L46-L49】. This can be shown in the demo as a separate isolated “secure” server box. 
Data Flow (sequence): User → UI sends query → Backend → RAG fetches docs → Backend orchestrates
agent → LLM called → Backend processes output → UI displays result. All inter-service calls are internal to
the enterprise network. 
Deployment Options:
On-Premise Server: All components run on a local data center or a closed LAN. Containers (Docker)
or a Kubernetes cluster could host each service.

5. Data Requirements & Sample Data
We need industrial domain data to demo: e.g. oil refinery manuals, engineering specs, safety procedures. In
absence of real confidential data, we use: 
Public Corpora: Technical manuals from open sources (e.g. open PDFs of engineering handbooks,
safety bulletins, oil industry reports). 
Wikimedia: Petroleum engineering, chemical processing, electronics schematics (images) from
Wikipedia/Wikimedia Commons. 
Synthetic Data: Use GPT-4 or open LLM to generate realistic Q&A pairs and technical docs (e.g.
“generate a short maintenance manual for a chemical reactor”). This is allowable as a training set or
seed content. 
Open Datasets: Kaggle or academic datasets (e.g. the “DSM-ICSD” Materials Project for chemistry, or
NASA open archives for machinery data). Even generic QA sets (SQuAD, ELI5) can be fine-tuned for
our demo tasks. 
Private Simulated Documents: Create faux “confidential” docs: e.g. simulate an MRPL SOP or an oil
pipeline manual with realistic content. Ensure no actual secrets. 
For vector search, we’ll split long documents into chunks (e.g. 500 tokens) and embed with an open model
(MPNet). As a fallback, we can simply store full text and do keyword match if embedding fails. 
We do not need huge training datasets; the focus is retrieval and prompting. During the 36h hack, we can
use small sets (e.g. 5–10 synthetic docs, 50 Q&A pairs). After the hack, one could expand to more
documents. 
No single “official dataset” exists for this niche problem, so our approach is to generate or gather domain-
relevant data from open sources. This demonstrates feasibility without violating confidentiality. 
6. Security, Privacy & Compliance Checklist
Threat Model:
External Attack: An attacker tries to intercept data. We mitigate by disabling all outbound
connections, using air-gapped or firewall. 
Internal Misuse: Rogue user with access. We mitigate via strong authentication (Keycloak) and role-
based access control – e.g. only “Trustworthy Agents” role can view logs. 
Model Leakage: Concern that the LLM might output sensitive data it saw. We guard by not uploading
any truly sensitive data. For compliance, we log every model output to trace any leak. 
Mitigations:
Encryption: Encrypt data-at-rest (disk encryption) and in-transit (TLS for UI/backend). 
Access Control: Use LDAP/AD or Keycloak to enforce user roles; only admins can manage the system. 
Data Residency: All data (documents, embeddings, logs) stay in on-prem storage. No cloud or internet
access.【13†L318-L322】 
Audit Logging: Log every user query, prompt, agent action and LLM call (timestamps, content
hashes). Secure logs with write-once permissions (append-only). Show example log entry in demo. 
Anomaly Detection: (Optional) Monitor for unusual agent behavior (infinite loops, excessive token
use).

9. Risks, Limitations & Metrics
Technical Risks:
Model Performance: Open LLMs may underperform on some tasks vs GPT-4. Mitigation: use multi-
model routing (use smaller model for simple tasks, larger one for complex). 
Integration Complexity: Orchestrating vision+language+tools is complex. We limit scope in MVP (e.g.
one vision model, one retrieval model). 
Limitations:
Resource Needs: Large models need GPUs and memory; on-prem infra cost can be high. For demo,
we use quantized 7–13B models. 
Domain Coverage: The system is only as good as its knowledge base. If data is missing, answers will
be wrong. We stress that it’s an augmentation tool, not a replacement for experts. 
Evaluation Metrics:
Accuracy: For factual Q&A, measure correctness against ground truth (could use a small test set of
known Q&A). Expect ≥80% accuracy on narrow domain queries. 
Latency: Responses should appear in a few seconds (target < 5s for text queries on GPU). 
Throughput: Agents should process batch queries with minimal queue. 
Security Audit: We will “prove” privacy by logs and (if used) TEE attestation. Metrics include “0 external
API calls”, “100% encrypted data logs.” 
User Satisfaction: In real deployment, measure via surveys of trust in AI answers. For SIH hack, clarity
of demo is key.
